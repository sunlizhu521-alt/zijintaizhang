# 资金台账

基于四类 Excel 来源，集中查看付款计划、台账累计已付与剩余、三类预估及待核对问题。原始文件、解析结果、历史版本、用户和系统记录统一保存在服务器 SQLite 数据库中。

代码仓库：<https://github.com/sunlizhu521-alt/zijintaizhang>。部署状态以 GitHub Actions、健康接口和页面验收结果为准。

## 资金付款分析

资金台账侧栏新增“资金付款分析”，文件管理的“对公付款OA流程”页签使用独立 `corporate_oa` 槽位，原四类计划来源与资金付款台账口径不变。OA 读取流程编号、收款单位、业务所属公司、付款金额、币种、签字意见（兼容签字）；外币人民币金额取判断金额。上传整个快照，替换和恢复沿用原版本、权限、审计机制。

同号重复发票/分摊行只计一次；非谈判流程取签字中最晚有效“出纳执行”日期。谈判付款 sheet 的两类记录优先按已付分期批注的金额和完整日期统计，不叠加整笔 OA；无匹配 OA 的明确已付分期仍保留。缺年份、同格多个日期、金额缺失或来源冲突列入核对，不猜测、不让个别异常覆盖已确认总额。

`GET /payment-analysis` 及 `/payment-analysis/export` 使用看板与导出权限；`GET /oa-flows` 及 `/oa-flows/export` 使用文件与导出权限。筛选支持 year、supplier（关键词）、payer（精确值）；分析新增 paymentCategory（默认 procurement 采购付款，other 其他付款，all 全部付款），按当前有效付款节奏的正常付款及谈判付款表供应商名单完整匹配，忽略首尾空白，不限制 OA 号、付款主体或年份；替换或恢复付款节奏后立即重算分类。分析下钻支持 detailMonth、detailSupplier（精确值）、supplierSearch，OA 列表支持 flowCode、paymentState，保持全部流程。当前年与上年比较到同月同日，历史年份比较全年。图表、Top10、台账、核对事项及精确元值导出共用服务端统计；下载不局限当前分页。统计仅代表当前上传文件覆盖的数据。

独立入口：<https://129.211.9.242/jihuaguanli/>。黄色 WorkBuddy 工作台，按顺序包含每日计划、待办事项、选题每日灵感、工作复盘、生活复盘、读书笔记、好句笔记、运动打卡、每日学习汇报、心情日记、周复盘、每日工作记录输入、待办事项输入。本次先交付电脑端，手机端与桌面安装留待后续。

- 表单草稿保存在当前标签页、按账号隔离。保存使用版本校验，云端更新后旧草稿不能直接覆盖；批量提交期间锁定交互，失败保留未提交条目。删除为可恢复的回收站操作。

首次启用独立入口时，在既有 HTTPS server 中仅追加 `deploy/nginx-location.conf.example` 的 `/jihuaguanli` 两个 location，执行 `nginx -t` 成功后 reload。仍代理至本项目 `127.0.0.1:4010`，不改变根路由、资金台账、采购订单、证书、端口或授权。代码推送本身不会自动安装这两段 Nginx 配置，部署后需同时验收新入口、相对资源及原入口重定向。

## 供应商交付管理

独立入口：<https://129.211.9.242/gongyingshangjiaofu/>，与资金台账并列。沿用已有账号、看板、文件、上传、恢复和导出权限；不新增账号或开放业务数据。三个独立槽位为金蝶采购订单、采购入库单、收料通知单，不参与资金统计，也不覆盖采购订单跟进页面的归档文件。

- 支持 `.xls` / `.xlsx`，每份不超过 20 MiB；保留原文件、所有原始列、历史版本和恢复能力。按前 20 行的表头名称识别字段，不依赖固定列号或总列数。额外列和可选列增减不影响读取；关键列缺失、重复表头或不明确日期会提示核对，不替代业务字段。预览可查看字段映射，详情可查看全部原始列。
- 用户已确认采购日期作为订单创建日期。以采购订单“单据编号”为主键，分别映射收料通知单和采购入库单的“源单单号”（兼容“源单编号”）；订单内结合物料与订单行核对。入库源单为收料单号时，保留经收料单唯一追溯采购订单。收料和入库的数量、日期、状态及指标在同一看板并列展示，不相加，不再提供口径切换；状态筛选保留任一交付类型符合条件的订单，导出同时包含两类结果。
- 用户已确认同物料使用相同计量单位；未导出单位时保留为空。同物料可比较，明确单位冲突须核对，不跨物料相加数量。空、负数、未来交付、重复和歧义记录不作为有效交付；零数量行保留。原订单的累计入库数量仅作为原始字段，不替代实际入库单依据。
- 指标包括交齐率、按期交齐率、延期、7 天内到期、供应商及交期月趋势。按期交齐率以截至统计日的有效到期正数量订单行为分母；受歧义影响的行明确标为待核对并排除，不显示为正常交付。超交数量保留并提示，完成率逐行封顶。
- 同订单同物料多交期时，备注计划批次、收料与入库单据批次数、每批日期及数量；未明确订单行归属时不按 FIFO 分配，也不将组级数量重复计入每行。批次依据为单号与业务日期，不推断物理发货车次。关闭订单保留历史交付指标与差额，但停止延期和临期预警。超出当前订单文件范围的历史单据单独折叠显示。
- 人工维护生产进度、发货状态、预计发货日期、负责人、产品/规格/数量/标签/收货信息核验、异常及协调措施。跟进保存检查 revision 并记录操作；替换文件不覆盖人工跟进，同一订单行更换物料不会套用旧核验。原表未提供的信息不自动认定一致。
- 支持供应商、交期月、状态及关键词筛选、排序、分页、明细展开和按筛选导出 Excel；导出包含指标、批次、明细及数据范围说明。使用北京时间，日期显示 `YYYY-MM-DD`，Excel 日期保留原生日期格式。

前端沿用 React/Vite，独立页只复用同源 `/zijintaizhang/api` 会话与资源。后台接口为 `/delivery/*`，跟进存储于独立 `delivery_followups` 表。SheetJS 0.20.3 仅用于交付文件的 XLS 与大表读取，来自[官方安装源](https://docs.sheetjs.com/docs/getting-started/installation/nodejs/)，锁文件固定完整性；财务解析仍使用原 ExcelJS。解析在串行隔离 Worker 中执行，交付 Worker 内存上限 384 MiB，限时 30 秒；宏、加密及不安全结构会被拒绝。

首次部署在现有 HTTPS server 已引用的 `zijintaizhang.locations.conf` 中追加 `deploy/nginx-location.conf.example` 的 `/gongyingshangjiaofu` 两段，先备份、`nginx -t` 成功后 reload。保持原证书、端口、其它项目与权限。

实际 6 万余条交付记录按生产 256 MiB 堆限制验证通过；看板仅返回当前订单相关明细，范围外单据按页加载，完整 Excel 用流式写出。保留 256 MiB 堆限制，仅将 PM2 RSS 重启阈值从 384 MiB 调为 640 MiB，覆盖实测约 524 MiB 峰值，避免正常解析或导出被误重启。

验证覆盖三类上传、版本恢复、原文件字节一致、财务隔离、旧 XLS、变动列、分批、空零异常、追溯歧义、关闭规则、权限、CSRF、并发跟进和持久化；真实样表只在本机验证，不提交仓库或自动上传线上。

## 架构

- 前端：React 19 + Vite，页面和静态资源前缀为 `/zijintaizhang/`。
- 后端：Express 5，API 前缀为 `/zijintaizhang/api`。
- 存储：Node 内置 `node:sqlite`，启用 WAL、外键及事务；原始 Excel 以 BLOB 保存在数据库。
- Excel：ExcelJS 读取工作簿，yauzl 检查压缩结构；解析在限时、限内存的独立 Worker 中执行，同一进程一次处理一个文件。
- 生产：Nginx HTTPS → `127.0.0.1:4010` → PM2 单实例；每个发布包携带自己的 Linux x64 Node 22，不替换服务器全局 Node。

主要代码：`src/` 为页面，`server/parser.js` 为解析口径，`server/dashboard.js` 为汇总规则，`server/storage.js` 为文件版本，`server/auth.js` 为认证权限，`shared/constants.js` 为槽位、类别和权限定义。

## 本地运行与验证

建议使用最新 Node 22，至少为 22.16.0，以支持部署备份脚本使用的 `node:sqlite.backup`。首次运行：

```bash
npm ci --ignore-scripts
npm test
npm run build
npm run admin:init
npm start
```

访问 <http://127.0.0.1:4010/zijintaizhang/>。`admin:init` 必须在交互式 Terminal 中运行，隐藏输入两次密码；没有默认账号密码，已有管理员时不会重复初始化。

开发时分别在两个 Terminal 中运行：

```bash
npm run dev
```

```bash
npm run client
```

前端开发地址为 <http://127.0.0.1:5173/zijintaizhang/>，Vite 将 API 转发至本机 4010。测试使用合成数据和临时数据库；接口测试需要允许监听本机临时端口。

本地默认数据库为 `data/zijintaizhang.sqlite`。可用 `DATA_DIR` 指定数据目录；服务支持 `HOST`、`PORT`。生产模式还要求 HTTPS `PUBLIC_ORIGIN`，本项目反向代理使用 `TRUST_PROXY=loopback`。生产配置由 PM2 文件读取，不在代码中保存管理员密码。

## 四个文件槽位与统计口径

每个槽位只有一个当前有效版本。上传先预览，再确认启用；数据校验失败、解析超时或并发版本冲突时保留原有效版本。待上传草稿一小时后失效。同一用户重新选择同一槽位的文件会替换该槽位尚未启用的草稿。

| 槽位 | 读取范围 | 付款月份与金额来源 |
| --- | --- | --- |
| 付款节奏 | 新上传须包含 `谈判付款`、`正常付款`、`付款进度整理` | 前两张表提供业务记录；进度表只提供付款依据，不增加金额 |
| 发货计划预估 | 选择符合预估模板的工作表 | `预估付款月份`、`申请付款金额` |
| 售后配件预估 | 同上 | 同上 |
| 已发货未登记台账预估 | 同上 | 同上 |

付款节奏必需字段：

- 两张表均需供应商、付款主体、摘要、已付金额、剩余付款金额（或剩余金额）。供应商表头支持 `供应商` 或 `供应商名称`。
- 谈判付款另需 `OA-申请付款金额`、`应付款时间`、`是否谈判分批`，以及至少一列带年份的月支付表头；`是否谈判分批` 必须填写“是”或“否”。
- 正常付款另需 `本次申请付款金额`、`应付时间`。
- 付款进度整理需流程号（支持 `对公付款OA号`）、申请付款金额、供应商名称、付款主体、是否已付款。

三个预估槽位的模板必需表头为：`预估付款月份`、`供应商名称`、`付款主体`、`摘要`、`申请付款金额`、`账期`、`备注`。系统在前十行识别表头；预估工作表默认选择格式有效的可见表，名称含“原始、备份、汇总、合计”的表默认不计入，可在预览中人工选择符合格式的表。

统计规则：

- `谈判付款` 工作表按 `是否谈判分批` 分类：“是”为“谈判付款-谈判付款表”，“否”为“正常付款-谈判付款表”；两类仍读取该表的带年份月支付列。`正常付款` 工作表按预估时间拆分已对账与未完成对账，金额读取本次申请付款金额。分类空白或其他内容会提示原表位置并拒绝导入，避免误归类。
- 看板父子表默认显示谈判付款、正常付款及总合计。点击“正常付款”可单独展开五行汇总：正常付款-谈判付款表、正常付款-资金台账表、正常付款-已付货未对账预估、正常付款-配件发货预估、正常付款-发货计划预估。其中资金台账表合并原正常对账与未完成对账两类，仅汇总展示，原始记录类别不变。父级只从原始分类求和，展开不重复计算；只有当前有效版本参与汇总。金额明细弹窗支持按供应商部分名称搜索，合计、分页和下载均跟随搜索范围。
- 正常付款工作表的“预估时间”有内容时归为“正常付款-未完成对账”，按预估时间归月；其余归为“正常付款-正常对账表”，按应付时间归月。无有效预估日期时列入时间待定，不退回应付时间。旧文件没有该列时保留在“正常付款-正常对账表”；原表“是否对账”字段保留供核对，不用于本次分类。公式没有可用日期结果时保留未完成对账并提示核对，不推测日期。
- 看板依次排列“月度付款汇总”“供应商明细”“时间待定付款汇总”和“待核对事项”。待定汇总及其各级分类、待核对事项默认收起。两张汇总表采用相同父子结构：月度表每月显示已付、未付、本月合计及所选期间合计；待定表只显示一组已付、未付、合计。两表均显示元及万元并可下钻；有效零金额保留，无待定记录时显示空状态。
- 汇总表以每类三行“已付、未付、合计”排列，分类合并单元格，分组底色和边线区分谈判、正常与预估。点击金额后每笔月份计划以表格显示，选中金额列高亮并展示全部明细合计；付款依据、原始字段和批注也在表格内展开，不使用卡片。
- 供应商明细按供应商合并为一行，显示分类、当前筛选计划总金额（含待定）、月份及查看详情。展开后每笔来源记录一行，展示付款主体、数据类别、跟单员、摘要、金额、谈判及分批安排、申请、节点、支付状态和孙立柱备注；原表完整分批安排不受月份筛选裁剪，也不重复计入总金额。未明确分批次数时仅展示已登记日期金额列数（含零），不推算缺失安排；日期显示 YYYY-MM-DD。窄屏将展开明细改为纵向字段表，保持无横向滚动。
- 供应商详情的“申请时间”按用户确认仅由“什么时间”更名，仍显示原分批日期列，不更换日期来源，不影响付款时间或已付判定。
- 看板使用浏览器可用全宽。每月单元格纵向显示已付、未付和合计；月份过多或屏幕较窄时，按容器宽度向下续表，不横向滚动。看板明细与付款依据自动换行，汇总金额和导出口径不变。
- `谈判付款` 工作表的两类付款均按金额格批注识别：`付款时间（付款节奏跟进）：2026年11月2日` 或 `付款时间：2026年11月2日` 这样的明确付款时间直接代表已付，无需另写“已付／已支付”；也保留“日期＋已付／已支付”写法。付款日期优先取明确付款时间，未写年份不猜年份，金额仍按原计划列归月。申请日期不代表已付；部分付款金额不明、冲突或已付超出月额时显示待核对。解析规则升级后自动重建保存文件的解析缓存，无需重新上传。
- 正常付款工作表和三类预估按流程号关联当前有效付款节奏的进度表，同号多笔用申请金额、供应商及付款主体消歧。仅明确匹配“已付款”计已付；未匹配、无流程号、空状态、“未付款”“重新申请”或匹配冲突均计未付并说明原因。归档状态不作为已付依据，申请日期不作为付款日期。
- 付款计划和预估按月份筛选；台账累计已付、剩余只受供应商、付款主体、跟单员、类别筛选，不受月份筛选影响。
- 日期缺失、缺少年份或格式不明确时进入独立待定表，不计入月度表和所选期间合计。月份范围只影响月度表，供应商、主体、跟单员及类别筛选同时影响两表；选择“时间待定”时只展示待定表。谈判付款所有月支付单元格均为空时，将原申请金额列入时间待定；有月计划时保留这些计划，不自动分摊差额。
- 申请金额、原台账已付、剩余及月支付等金额为空，或金额公式没有已保存的计算结果时，按 0 保存并参与统计；原始字段和原文件保留。原台账累计已付与剩余不被新规则覆盖，和月内识别结果不一致时提示核对。
- 金额按“分”存储和求和，超过两位小数按四舍五入处理。负金额保留并提示复核；超出安全计算范围时拒绝导入或汇总。
- 页面万元金额直接截取两位小数，不四舍五入（899,968 元显示为 89.99 万元）；汇总仍使用原始分值，Excel 导出保留精确元值。
- 月计划合计与申请金额不一致、已付加剩余不一致、状态矛盾、缺失付款主体等进入待核对问题，不自动改写原值。
- 相同流程号，以及供应商、付款主体、计划金额相同且月份相同或相邻的记录，会提示可能重复；不自动去重或扣减金额。
- 明细保留来源文件、工作表、行号、原始字段、备注和单元格批注，便于回查。下载原始文件返回上传时的原文件。
- 进度关联在查询时进行：替换或恢复付款节奏后刷新即生效，不用重传预估。历史付款节奏预览用自身进度；历史预估预览用当前进度并标注版本。历史缺表/字段的版本可保留及恢复，相关付款按未付并提示；新上传缺表/字段拒绝替换。解析缓存升级只涉及四个资金槽位，原文件和历史元信息保留，采购订单归档不受影响。
- 导出包含“月度付款汇总”“时间待定付款汇总”两张汇总表，以及筛选明细、统计口径和待核对事项；明细包含付款日期及依据版本。

仅接受不超过 20 MiB 的 `.xlsx`；不支持加密文件、宏或外部工作簿链接。解压内容上限 200 MiB、压缩条目上限 5,000、有效记录上限 100,000。每次解析限时 30 秒；文件即使小于上传大小限制，也可能因解压体积、解析内存或耗时超限而被拒绝。

服务器不会重新计算 Excel 公式。金额公式有已保存结果时读取该结果，无已保存结果时按 0 保存；非法金额文本、公式错误值或超出安全计算范围仍拒绝导入。若需使用公式实际结果，请先在 Excel 或 WPS 中完成计算并保存，再上传。

规则更新后，服务器已保存的当前及历史文件自动重新解析，缓存同步采用新分类、空金额及付款状态口径，原文件、上传人、上传时间和版本记录保留。导出包含父子汇总、筛选明细及付款批注依据，金额以元保存为数字。

## 用户、权限与记录

管理员在系统内创建用户、分配权限、停用账号和重置密码。用户首次使用新建或重置的密码登录时必须先修改密码；密码须为 6 至 128 个字符，且同时包含英文字母（A–Z、a–z）和数字（0–9），可以额外包含符号或其他字符。初始化、创建、修改和重置密码采用同一规则。最后一位启用中的管理员不能被停用或降级。

权限由服务器接口强制校验：

| 权限 | 对应能力 |
| --- | --- |
| `dashboard` | 查看资金看板 |
| `files` | 查看文件管理、版本和解析明细 |
| `upload` | 上传预览并替换文件，同时需要 `files` |
| `download` | 下载原始文件，同时需要 `files` |
| `restore` | 恢复历史版本，同时需要 `files` |
| `export` | 导出查询结果，同时需要看板或对应记录的查看权限 |
| `logsLogin`、`logsOperation`、`logsSecurity` | 分别查看登录、操作、安全异常记录 |

管理员拥有全部权限及用户管理能力。停用、重置密码或修改权限会撤销该用户现有会话；自行修改密码会撤销旧会话并建立新会话。

密码使用 scrypt 哈希；会话最长 24 小时，数据库只保存会话 token 的哈希。生产 Cookie 使用 HttpOnly、Secure、SameSite=Strict；写入接口验证 CSRF 和请求来源。Nginx 覆盖客户端传入的转发 IP 头，后端只信任回环代理。

登录记录区分成功登录与失败尝试：失败记录中的账号仅是提交的账号，不能视为已确认身份。操作记录包括文件启用/恢复/下载/导出及用户权限变更。安全异常包括连续登录失败、请求频率超限、越权、CSRF/来源错误和疑似路径探测。

当前限制为每 IP 每分钟 120 次 API 请求；账号或 IP 在 15 分钟内累计五次登录失败后短时限制 15 分钟。成功登录不清零同 IP 的失败计数。限流计数为单进程内存状态，重启会清零。安全异常是排查线索，不等于已确认攻击或识别了攻击者。

系统记录使用 UTC 存储，页面按北京时间显示；启动时及每日任务清理超过 365 天的记录。日志不保存密码、会话 token 或完整请求正文。

`.github/workflows/deploy.yml` 的流程：

1. PR 运行测试与构建；`main` 推送或在 `main` 手动运行时继续部署。同一分支的任务串行，不取消正在执行的部署。
2. 在 Ubuntu 24.04 + 最新 Node 22 上安装锁定依赖、测试、构建，再仅安装生产依赖并打包独立 Node 二进制及校验信息。
3. 将发布包上传到 Actions Artifact，保留一天。Runner 用本次任务的短期 `GITHUB_TOKEN`（`actions: read`）取得临时 HTTPS 地址，通过固定 known_hosts 校验的 SSH 只发送小型下载清单。服务器不保存或接收 GitHub token。
4. 接收端只接受 GitHub Actions 使用的 `productionresultssa<数字>.blob.core.windows.net` HTTPS 存储地址；拒绝其他域名、非443端口、私网 DNS 结果和重定向，连接固定到已验证的公网 IP。为适应跨境链路，使用最多8个并行分段，总限时20分钟、单次连接限时10秒；严格核对每段 Content-Range，再核验完整 ZIP 和 tar 的 SHA256、预期大小及 ZIP 内唯一文件，执行原 tar 的路径白名单、体积、重复路径和 runtime 校验。临时下载URL不写日志；失败最多重试三次，每次重新获取签名地址。
5. 校验 4010 未占用，或确认其属于本项目的既有 PM2 进程；检查现有数据库备份和完整性后，切换 `current`，只重启 `zijintaizhang`。
6. 检查本机及 HTTPS 健康接口返回的应用名和提交 SHA；发布窗口内失败时尝试恢复前一版本。Actions 再从外部检查 HTTPS 健康接口和首页。

服务器不执行 npm 安装或前端构建，也不升级全局 Node。旧代码版本保留在 `releases/`；同一提交的发布目录保持不变，失败版本需审查后处理或通过新提交发布。

## 备份、版本恢复与边界

- **文件历史版本恢复**：在页面选择某一槽位的历史版本，改变该槽位的当前有效版本；其他槽位、原始版本和用户不变。并发更新会被版本号校验阻止。
- **发布前备份**：已有数据库时，部署脚本使用 SQLite 在线备份，将 WAL 中已提交内容一并保存到 `shared/backups/predeploy-*.sqlite`，并执行 `PRAGMA quick_check`。备份包含用户、文件原件、所有文件版本及系统记录。
- **代码发布回切**：恢复前一个 `current` 和本项目 PM2 进程，不自动恢复数据库，不抹去发布期间产生的数据。后续数据库结构变更须考虑旧版本兼容性。
- **完整数据库恢复**：属于运维操作。先确认回退时间范围，只停止本项目；保留当前数据库及 WAL/SHM，再验证并恢复选定备份，隔离旧 WAL/SHM 后启动并验收。恢复会回退备份之后的账号、上传版本及系统记录，不能与普通代码回切混同。

当前提供发布前的本机备份；定时、异地备份和备份保留期需另行配置。文件历史版本和发布备份不会自动清理，需监控磁盘空间。审计记录清理期限为 365 天，与文件版本和备份保留无关。

`.gitignore` 排除运行数据、SQLite、Excel/CSV、日志、环境文件、依赖和构建产物。业务原文件与数据库不应提交到代码仓库。

左侧“供应商管理”集中提供采购履约表上传、供应商名单上传、模板下载及名单维护；“评价管理”只保留月份开关、自动识别的评价人、参评状态和报告。履约表导入按右上角所选评价月份分配；月份未开启、暂停或结月时，可前往“评价管理”处理后返回上传。

管理员在“供应商管理”导入供应商名单（`.xlsx`，最多20MiB、5000条；先预览后确认）或手工维护；只需“供应商名称”一列（兼容“供应商”“供应商简称”），名称完全相同的重复行只保留一条，相互冲突的状态拒绝导入；未填写状态时保留已有启停状态。页面、模板和报告不显示或要求供应商编码，内部历史关联保持不变，重命名/停用保留历史。名单原文件保存在独立库中。评价人按履约表的工作表命名人自动安排；同一家出现在两个人的工作表中，两个人分别评分，汇总为已评人数／应评人数，不提供手工或批量分配按钮。可复制上月名单；停用账号不改写既有月份的应评人数。评分人只能修改本人被分配的评分、查看本人记录与获分配供应商汇总。不能读取他人明细/备注；导出同样校验。跨期汇总包含未授权月份时不显示该汇总。

“采购履约表 · 按工作表分配”独立槽位按工作表命名人匹配评级账号，忽略采购下单人、创建人及下单月份。支持前10行中的供应商/供应商名称/供应商简称列，最多20MiB、64张表、20000行、1000个名称；隐藏表和未识别表列明未纳入原因。账号仅精确匹配且须启用并有评分权限；未匹配工作表默认不纳入，管理员可在预览中选择已有账号，不自动创建账号。供应商相同名称自动对应；相近名称（含同一文件内的简称与全称）只提出对比，由管理员点击“是，同一家”或“不是同一家”，不自动合并不同名称。无需手工选择新增或编号；未对应的名称在最终确认时自动建档。同一家共用记录，来源原文及行号保留。按所选月份追加评价人，多张表对应同一供应商时合并人员，保留原有分配与所有评分；不参评冲突须先人工处理。暂停、结月、预览过期或账号/供应商/范围并发变化时拒绝整批提交。已确认文件原件、来源工作表和行号、操作记录长期保存，仅管理员可下载原件；普通评价人仍仅能访问自己的授权范围。

未结月可撤回修改，撤回即退出均分。月度取已提交完整个人评分等权平均，缺评不补零；季度和年度对已结月且有评分的月均分等权平均，显示有效月数与缺评/阶段标记。中间不舍入，最终成绩四舍五入至1位后定级：A≥90，B≥80，C≥70，其余D；无分不定级。规则修订仅作用于以后新开启的月份。

管理员可临时关闭评分月份并随时恢复：暂停期间禁止保存、提交、撤回评分及调整评价人，仍可查看、导出与跟进过程整改；不生成结月快照、不计入已结月期间汇总，所有已有数据保留。临时关闭与恢复均校验管理员权限及版本并记录操作。恢复后可继续评分或结月。

管理员手动结月，存在缺评时须确认并记录原因；评分锁定，月报快照以V1/V2等递增保留。重开须填原因，再次结月生成新版本。过程记录可在结月后继续跟进整改；历史报告保留当时状态。评价草稿在服务器手动保存；未保存输入暂存在当前标签页且按账号、月份、供应商隔离，退出登录时清理。并发修改返回409，不覆盖他人的更新。

首次启用需先在 HTTPS server 添加示例配置中的评级独立 location，`nginx -t` 通过后 reload。**生产发布使用服务器 `bin/deploy-release.sh`，普通发布不会自动覆盖它**；首次上线前应安装经校验的新脚本，新脚本会逐库在线备份及校验两个数据库。任一备份失败中止发布。发布回切只切代码，不回退数据库；恢复某个库时明确选择该库并保留另一个库。

管理员初始化仅一次：使用生产 Node 和 DATA_DIR 运行 `scripts/rating-admin-init.js`，不带参数只列出名称匹配孙立柱的启用管理员账号；核对唯一账号后以该用户名作为唯一参数运行。来源库只读，仅复制该管理员的登录名、显示名、密码哈希和首次改密状态，生成独立用户ID并立即备份；不复制其他账号或会话，不同步后续密码，不输出凭据。目标库已有用户时拒绝重复初始化。
